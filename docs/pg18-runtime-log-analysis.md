# PG18 Runtime Log Analysis — Strapi, supabase_admin and safeupdate

Status: EVIDENCE_BASED_ANALYSIS
Date: 2026-06-12

## 1. Question 1: why is something connecting to database `strapi`?

The source is an existing Docker Swarm service:

```text
service: strapi_strapi
image: elestio/strapi-development:latest
network: portainer_agent_network
```

Runtime evidence collected from the live host:

```text
strapi_strapi is running on portainer_agent_network.
postgres18_postgres is also running on portainer_agent_network.
postgres_postgres is also running on portainer_agent_network.
```

The Strapi service is configured with non-secret database routing values:

```text
dbclient: postgres
dbhost: postgres
dbname: strapi
dbuser: postgres
dbport: 5432
```

Inside the Strapi container, Docker DNS resolves `postgres` ambiguously:

```text
postgres -> 10.0.1.28
postgres -> 10.0.1.112
postgres18_postgres -> 10.0.1.112
postgres_postgres -> 10.0.1.28
```

The Swarm VIPs confirm:

```text
postgres_postgres   -> 10.0.1.28 on portainer_agent_network
postgres18_postgres -> 10.0.1.112 on portainer_agent_network
```

Therefore, the repeated log lines:

```text
postgres@strapi FATAL: database "strapi" does not exist
```

are not generated by the PG18 realtime proof. They are generated by the running Strapi service trying to connect as user `postgres` to database `strapi` through host name `postgres`, which resolves to both the PG17 and PG18 Postgres services on the same overlay network.

## 2. What is wrong with this?

There are two separate issues:

1. Strapi expects a database named `strapi`, but the target service it reaches does not have that database.
2. The hostname `postgres` is ambiguous because both `postgres_postgres` and `postgres18_postgres` are discoverable by that name in the Swarm network.

This is a service-network/configuration issue, not a PG18 image-build issue.

## 3. Correct action for `strapi`

Do not create a `strapi` database inside PG18 just to silence logs unless Strapi is intentionally supposed to consume PG18.

Correct options:

1. If Strapi should use the existing PG17 stack, set its DB host to the explicit service name/VIP for PG17, e.g. `postgres_postgres`, and ensure the `strapi` database exists there.
2. If Strapi should use PG18, explicitly set host to `postgres18_postgres` and intentionally create/manage the `strapi` database as a project consumer.
3. If Strapi is unrelated/no longer needed, stop or reconfigure the Strapi service rather than letting it probe PG18 forever.
4. Avoid generic service DNS names like `postgres` on shared Swarm networks when multiple Postgres services exist.

Because this repository task is PG18 base/stack work, not Strapi deployment, this analysis is informational and should not mutate the Strapi service without explicit scope.

## 4. Question 2: why is `supabase_admin` used?

`supabase_admin` is not a table. It is a database role/user that comes from the Supabase/Postgres image recipe.

Evidence in this repo:

```text
Dockerfile-18 sets POSTGRES_USER=supabase_admin
Dockerfile-18 sets POSTGRES_DB=postgres
Smoke scripts use psql -U supabase_admin -d postgres for administrative validation.
```

This is expected for image/runtime validation because the fork is based on the `supabase/postgres` build recipe.

However:

```text
supabase_admin is an image/admin/bootstrap role.
It should not be treated as a project application role.
```

Project-facing roles should be installed by DDL packages and should be explicitly named for their purpose, for example:

```text
authenticator
realtime_bridge
app_runtime
project_service_role
prop4you_app
```

The exact naming should be defined by the DDL package, not hardcoded into the image.

## 5. Question 3: what are `safeupdate_probe` errors?

`safeupdate_probe` is a test table used by smoke scripts to verify the `safeupdate` preload hook.

The intended positive test is:

1. Create `public.safeupdate_probe`.
2. Try `UPDATE public.safeupdate_probe SET val = val + 1;` without `WHERE`.
3. Expect failure:

```text
UPDATE requires a WHERE clause
```

4. Try `UPDATE ... WHERE id = 1`.
5. Expect success.
6. Drop the probe table.

The log line:

```text
ERROR: UPDATE requires a WHERE clause
```

is expected and means the `safeupdate` behavior is working.

The earlier lines:

```text
ERROR: relation "public.safeupdate_probe" does not exist
```

mean a probe attempted to update/drop the table before or after the table existed. This is likely from an earlier/non-deterministic smoke attempt or a race/stale command, not from the current corrected smoke script.

## 6. Correct action for `safeupdate_probe`

The correct action is not to remove the safeupdate test. The correct action is to make the smoke deterministic and explicit:

- create table and insert rows in the same checked step;
- run the expected failing update and assert the exact error;
- run the WHERE update and assert the final value;
- drop the table in cleanup;
- avoid emitting confusing stale relation errors.

This is why `scripts/smoke-pg18-realtime-v2.sh` exists for realtime v2 and why full-parity smoke should keep the same deterministic pattern.

## 7. Operational conclusion

- `strapi` log noise is external service configuration drift on the shared Swarm network.
- `supabase_admin` is expected for the Supabase/Postgres image recipe and smoke validation.
- `safeupdate_probe` is expected as a test object; only the missing-relation variant is undesirable log noise.
- PG18 base image/stack and project DDLs must remain separate.
